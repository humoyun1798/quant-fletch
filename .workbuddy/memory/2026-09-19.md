### 环境实测结论

- Docker 29.5.2 可用，守护进程正常，DockerRootDir 在 C 盘（C 盘当时仅剩 ~18G）。
- `uv.exe` 位于 `C:\Users\Administrator\.local\bin\uv.exe`（不在 bash PATH 里，需用绝对路径）。

- 项目要求 Python >= 3.14，本机原本没有，由 uv 自动下载 cpython-3.14（落在

### 宿主机侧踩坑（与项目无关）

- **uv 在宿主机无法完成构建**：`uv sync` 会在编译 `jsonpath==0.82.2` 收尾阶段失败。
  真实原因是 WorkBuddy 沙箱注入的 `sitecustomize.py` 禁止删除文件，而 Windows 回收站在
  沙箱内不可用，报 `SAFE_DELETE_FAIL_CLOSED / windows-sandbox-recycle-bin-unavailable`。
  **包本身编译是成功的**（wheel 已产出），仅删除临时 dist-info 时被拦。
  → 结论：需要跑 Python 构建时，Docker 内可正常完成；宿主机需绕开沙箱。

`5396-5495`、`7948-8047` 等区间。**5432 和 8000 都落在保留区内**，Docker 绑定会报

## 为跑起来而修的问题（compose 与 Dockerfile 原本多处不可用）

原 `docker/docker-compose.yml` + 两个 Dockerfile 存在 8 处缺陷，README 声称的
「一条命令开箱即用」不成立：

1. **db 服务启动即崩**：`read_only: true` + `cap_drop: ALL` 剥夺了 CAP_CHOWN/CAP_SETUID，
   官方 postgres 镜像无法 chmod 数据目录、无法 setuid 切用户 → exit 1。
   已实测复现。修法：去掉 `cap_drop`，加 `tmpfs: /var/run/postgresql` 与 `/tmp`。
2. **api 服务未映射端口**：compose 里 api 没有 `ports`，README 说的
   `localhost:8000/docs` 根本访问不到。已加 `18000:8000`。
3. **api healthcheck 用 curl**：`python:3.14-slim` 不含 curl → 永远 unhealthy →
   依赖它的 nuxt 永远不启动。已改为 python urllib 自检。
4. **Dockerfile.api 没拷 `uv.lock`**：`uv sync --frozen` 会直接失败。已补 COPY，
   并加 `--no-install-project`。
5. **Dockerfile.api 缺 `PYTHONPATH`**：源码用 `from db.duckdb import ...`
   这类以 src 为根的绝对导入（本地靠 pyproject 的 `pythonpath=["src"]`），
   容器内必须 `ENV PYTHONPATH=/app/src`，否则启动即 ImportError。
6. **Dockerfile.api 用了 Alpine 的 adduser**：`adduser -D -u 1001` 在 Debian 系的
   `python:3.14-slim` 上不识别 `-D`（exit 51）。已改为 `useradd --create-home --uid 1001`。
7. **前端代理指向错误**：compose 传的 `API_BASE_URL=http://api:8000` 代码里从未读取，
   `nuxt.config.ts` 的 routeRules 硬编码 `localhost:8000`（容器内指向自己）→ 前端所有
   `/api/**` 请求失败。已让 nuxt.config 从 `process.env.API_BASE_URL` 读取（构建期求值，
   故在 Dockerfile.web 里注入）。
8. **WebSocket 地址错误**：`web/app/config/api.ts` 生产分支写死
   `wss://${window.location.host}`，页面是 http 却用 wss（TLS 必失败），且该 WS 端点
   在 api 容器上。已改为可由构建期 `VITE_WS_ORIGIN` 注入（Dockerfile.web 里设为
   `ws://localhost:18000`）。

### 锁文件与 pnpm 版本（最耗时的一环）

- `corepack enable` 默认拉 pnpm 12.4.2 → 报 `ERR_PNPM_OUTDATED_LOCKFILE`：
  根 package.json 把 `@unocss/nuxt`、`@unocss/preset-web-fonts`、`typescript`
  改成了 `catalog:` 写法，web 把 `vitest` 改成 `catalog:test`，
  **但锁文件没重新生成**（`catalogs:` 段缺这 4 个条目，importer specifier 仍是具体版本号）。
  这是仓库自身 bug，任何 pnpm 版本都过不了 `--frozen-lockfile`，其 CI 大概率也是挂的。
- 尝试重新生成锁文件（`pnpm install --lockfile-only`）→ 被仓库自己的
  `trustPolicy: no-downgrade`（写在 `pnpm-workspace.yaml`）拦下：
  `semver@6.3.1 High-risk trust downgrade`。说明重新解析会把传递依赖降级，风险更大。
- **最终采用的做法**：手工把锁文件元数据对齐——补上 `catalogs:` 段缺失的 4 个条目
  （dev/typescript、test/vitest、unocss 下两个），并把 4 个 importer specifier 改成
  `catalog:*`。**所有已解析版本号一字未动**，只修元数据。
- 并把 Dockerfile.web 的 pnpm 从 corepack 默认版本改为**固定 `pnpm@9.15.9`**：
  与生成锁文件的版本一致，且 pnpm 9 不认识 `trustPolicy`，不会触发降级校验。
  （pnpm 12 即使锁文件一致，仍会因 `semver@6.3.1` 拒绝安装。）
- 原锁文件已备份为 `pnpm-lock.yaml.bak-20260919`。

## 关于「怎么获取买卖信号」——实测结论

### 信号产出路径（唯一一条）

系统**没有实时/当日信号接口**。信号只从回测结果里来：

1. `POST /api/v1/backtest`（或界面「策略工作室」）跑一次回测；
2. 结果里的 `signals` 是**每个调仓日的清单**（`action` = buy/sell + `target_weight`）；
3. **最后一期清单 ≈ 当前目标持仓**，可作为「现在该买/该卖」的答案。

界面上的「信号记录」页（`signals.vue`）只是把 `useBacktest()` 的结果按时间线渲染，
不跑回测就没有任何内容。

### 第 12 处缺陷：params 为空会导致回测直接失败

`routes/backtest.py` 的 `start_backtest()` 用 `params.get(pd_.name, pd_.default)` 校验参数，
但随后调用的是**原始 `params`**：

```python
for pd_ in param_defs:
    val = params.get(pd_.name, pd_.default)   # 仅用于校验
...
strategy.warmup(params)                        # ← 传的是原始 dict, 未合并默认值
```

而 `TrendMA.warmup()` 等实现是 `params['lookback']` 直接取值，所以
**POST 时 `params` 留空或缺项 → `KeyError` → 回测 failed**，报
`策略执行失败: 'lookback'`。（界面表单会带上全部参数，故 UI 不触发。）

**绕过方式**：调用 API 时必须显式传全部参数，可用 `/api/v1/strategies` 的
`params[].default` 补全。仓库根目录留了一个可直接运行的脚本
`qf_signal_probe.py`（用户可自行删除）。

### 实测结果（策略「带止损动量增强」，2024-01-01 ~ 2026-09-18，140 个调仓日）

绩效：`total_return 29.22%`、`annual_return 10.30%`、`sharpe 0.757`、
`max_drawdown -10.82%`、`win_rate 54.9%`。

⚠️ **但 `benchmark_return 44.36%`，`alpha = -15.13%` —— 显著跑输基准（沪深300）。**

最后一期（2026-09-14）清单：买入 159981 能源化工、512010 医药卫生、510880 红利、
518880 黄金 各 20%，卖出 512690 酒 ETF（回撤止损）。

其他观察：
- 全部 6 个策略的 `rebalance_freq` 都是 `weekly`，**周频调仓**，与用户现有的 MA10
  日频体系是两套完全不同的东西；标的池固定 30 只 ETF，不含用户自选股清单。
- `metrics.avg_turnover` 恒为 `0.0`，每期 `turnover` 也恒为 0 —— 疑似统计 bug（未修）。
  根因已定位：`base.py` 的 `generate_signals()` 里 `turnover=0.0` 是**写死的**，
  而 `_calc_metrics()` 只是对 signal_history 里的这个字段求平均。
- 策略名是中文（如「带止损动量增强」），API 调用需用中文名。

## 把用户的自有 MA10 策略移植进本项目的可行性分析

用户问「可不可以把我的 MA10 策略写进里面」。结论：**大部分可以，但有 2 处硬性障碍**。

### 框架机制（已读源码确认）

- `StrategyMeta.rebalance_freq` 支持 `"daily" | "weekly" | "monthly"`，
  `_is_rebalance_day()` 对 daily 恒返回 True → **每天跑完整流水线**，与 MA10 日频契合。
- 成交价 = 信号当日 `adj_close`（`_Portfolio._get_close`），即**当日收盘价撮合**。
  与「收盘破 MA10 全走」天然对应；但**无法模拟盘中执行**（如尾盘 14:30-14:57 挂单窗口）。
- `sell` 是 `self.shares.pop(code)` → **全量清仓，不支持部分减仓**（与「全走」一致）。
- `buy` 是 `self.shares.get(code,0) + qty` → **支持对已有持仓继续加仓**。
- 策略实例在整段回测中持久，可用 `on_day_end()` 维护自定义状态
  （建仓日、建仓价、上次清仓日等）→ 冷却期、最少持仓日数可实现。
- `risk_overlay()` 是止损与单标的上限的钩子。
- 但 `PortfolioState` **只有 date/cash/positions/positions_pct/total_value，
  没有成本价、没有建仓日期** → 成本价类规则须在策略内部自记。

### 障碍 1（硬）：引擎无法保留现金，「首仓 ≤40%」表达不出来

`self_loop.py` 的 `_Portfolio.execute()` 把买入权重**归一化**了：

```python
total_target = sum(s.target_weight for s in buy_signals)
weight = sig.target_weight / total_target      # 单个 0.4 → 0.4/0.4 = 1.0
target_cost = total_equity * weight * (1 + config.commission)
...
scale = available / total_cost if total_cost > available else 1.0
```

后果：**只要发出 buy 信号，就会把可用现金全部投出去**（scale 只是按现金上限缩减）。

- 想开一只 40% 仓位？→ 归一化成 100%，满仓买入。
- 已持 40% 想再开一只 20% 的仓、留 40% 现金？→ 不可能，会把剩余现金全砸进去。

而且这是引擎的**设计矛盾**：`generate_signals()` 里算
`cash_ratio = 1.0 - sum(target_weight)`，说明原意是**绝对权重**，
但 `execute()` 又把它归一化掉，导致 `cash_ratio` 与实际持仓永远对不上
（实测每期 cash_ratio 显示 0.2/0.6，但实际是满仓）。

**修法**：把 `weight = sig.target_weight / total_target` 改为直接使用
`sig.target_weight`（即绝对权重语义）。但这会**改变现有 6 个策略的仓位行为**
（它们现在依赖归一化实现等权满仓），属于需要用户拍板的改动。

### 障碍 2（硬）：无法建模盘中执行

回测只有日线，按收盘价撮合。用户规则中的「尾盘 14:30-14:57 挂单窗口」没有对应物。
影响：用户关心的「盘中提前判断导致卖飞」问题，在此回测框架内**测不出来**。

### 障碍 3（半）：浮盈加仓需自记成本价

成交价=当日 adj_close，可在策略内推算建仓价，属半可行。

### 2. 新策略 `api/src/strategies/ma10_trend.py`

`MA10Trend`，`meta.name = 'MA10 趋势跟踪'`，`rebalance_freq='daily'`，被
`importlib` 自动发现（现共 7 个策略）。参数：
`ma_period=10, max_deviation=0.015, stop_factor=0.995, confirm_days=2,
cooldown_days=3, min_hold_days=2, slope_lookback=5, require_slope_up=1`。

实现要点与踩坑：
- `filter_universe()` **刻意不过滤**，返回全池。因为引擎只对 signals 里的 sell 建仓，
  若把跌破 MA 的标的过滤掉，持仓就永远收不到卖出信号、仓位会卡死；出场逻辑全部
  放在 `allocate()` 里显式产生。
- `register()` **不声明引擎因子**：`FeatureService.resolve()` 是按 `facet.category`
  分派的，声明 `'momentum'` 会每个调仓日白算一次动量再 JOIN（用不到）。
- 入场**只对新标的发 buy**，不对已持仓标的发加仓信号（否则引擎归一化会把全部现金砸进去）。
- `warmup()` 一律 `params.get(k, default)`，规避后端不合并默认值的缺陷。

### 3. ⚠️ 引擎级严重缺陷：回测结果原本不可复现（已修）

**症状**：同一策略、同一参数、同一数据，多次运行结果在 **-17% ~ +89%** 之间乱跳。

**定位过程**（对照实验是关键）：
1. 同一进程内重复 5 次 → 5 个不同结果；polars `group_by` 连续 3 次返回 3 种行顺序
   → 先给 `score()` 的聚合结果加 `.sort('code')`，进程内变稳定。
2. 但**跨进程仍不一致**（45.3% vs 82.0%）。对照内置策略（`带止损动量增强`、
   `双均线动量轮动`）跑 3 个容器 → **指纹完全一致**，说明引擎本身可复现，
   问题出在 MA10 策略的某一处随进程变化的因素。
3. 排除浮点假设：polars `mean()` 的 MA 值 3 次容器一致，且与纯 Python 重算逐位相同。
4. 固定 `PYTHONHASHSEED=0` → 3 个容器结果完全一致 → **确认是字符串哈希顺序**。

**根因（两处叠加）**：
- **策略侧**：`allocate()` 里 `for code in held:` 遍历的是 `set`，其迭代顺序由
  字符串哈希种子决定。卖出顺序 → 影响引擎里 `self.cash += ...` 的**浮点累加顺序**
  （浮点加法不满足结合律），末位差异一路传导到买入的 `available`/`scale`。
  → 已改 `for code in sorted(held):`
- **引擎侧（更严重）**：`_Portfolio.execute()` 里

  ```python
  actual_cost = target_cost * scale
  if actual_cost > 0 and actual_cost <= self.cash:   # 临界判断后【整笔丢弃】
  ```
  按比例缩放后各笔目标成本之和 ≈ 可用现金，末位浮点误差会让**最后一笔恰好超出而被
  整笔丢弃** —— 丢的是整个仓位，不是舍入零头，且丢哪一笔取决于顺序。
  已改为 `actual_cost = min(target_cost * scale, self.cash)` **截断而非丢弃**。

**修复后验证**：3 个容器（随机哈希种子）+ `PYTHONHASHSEED=0` 全部得到同一指纹
`f95e0587bf79` → 顺序无关、可复现。
副作用：`带止损动量增强` 由 18.8% 变为 **19.2%**（此前确有买单被误丢）。

### 4. 最终回测结果（37 只池，2025-01-01 ~ 2026-09-18，417 个交易日，可复现）

| 指标 | MA10 趋势跟踪 | 基准（沪深300） |
|---|---|---|
| 总收益 | **+5.34%** | +23.86% |
| 年化 | 3.19% | — |
| 夏普 | **0.005** | — |
| 最大回撤 | **-49.02%** | — |
| alpha | **-18.52%** | — |

**结论：默认参数下，这套裸 MA10 规则在 37 只 ETF 池上显著跑输基准，且回撤接近腰斩。**
原因：策略对**所有**满足条件的标的都建仓（无 top-N 选择、无仓位控制），
日均约 2.3 笔买入，在震荡市被反复打脸，是典型的 whipsaw 机器。
（注：同一策略在 29 只池上曾跑出 81.7% —— 池子成分对结果影响极大，说明结论脆弱。）

### 5. 顺带确认的数据事实（回答用户「是否必须等下午 3 点」）

- **分钟线是实时的**：`sources/eastmoney.py` 的 `fetch_minute()` 走
  `ak.stock_zh_a_minute`（Sina 接口），**盘中即能取到当日 5 分钟 K 线**，
  已存入 `etf_minute`（每只 1970 根 ≈ 最近 41 个交易日）。
- **日线当日那根**要收盘后才定稿（约 15:00-15:30），但 MA10 只需前 10 个交易日收盘。
- **真正的卡点是系统没有调度器**：依赖里没有 APScheduler/cron，seed 是一次性动作，
  之后必须手动调 `POST /api/v1/system/update`，否则日线永远停在 2026-09-18。
- **复权口径**：`clean_etf_data()` 在无 `adj_close_ref` 时令 `adj_close = close`；
  且本次 seed 中东财源被 `RemoteDisconnected` 打断、全部降级走 Sina，
  所以库里 `adj_close` 实为**不复权**价（与 README「尚未启用前复权」一致）。
  盘中实时价同为不复权，口径一致可直接比较；但**分红除权日会制造假跌破信号**。

### 遗留可做项

- `generate_signals()` 里 `turnover=0.0` 写死 → 换手统计恒为 0。
- `system.py` 判断 `status == 'running'` 而 seed 写的是 `'seeding'` → 初始化中不显示进度。
- 后端路由不合并参数默认值 → `params` 留空即 KeyError（内置 6 个策略全都中招）。
- `execute()` 用归一化权重 → 无法表达留现金/首仓上限。
- MA10 策略可补：top-N 选择、更长回测区间、按池子成分做稳健性检验。
