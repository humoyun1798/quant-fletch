## 用户报障：「为什么数据回测没有 2026 年的数据」

### 结论：不是数据缺失，是**日期被硬编码写死**

`web/app/pages/strategy.vue` 的 `startBacktest()` 里：

```ts
const config: BacktestConfig = {
  strategy: selected.value,
  params: { ...params.value },
  start_date: '2020-01-01',
  end_date: '2025-12-31',   // ← 硬编码, 界面回测永远只跑到 2025 年底
  benchmark: '510300.SH',
}
```

后端 `routes/backtest.py` 的默认值同样是硬编码的 `'2025-12-31'`：

```python
start_date_str = body.get('start_date', '2020-01-01')
end_date_str = body.get('end_date', '2025-12-31')
```

所以**界面和 API 两条路径都拿不到 2026 年数据**，与数据源、seed 都无关。

### 数据侧核实（确认数据是齐全的）

`etf_daily` 共 81,999 行，日期范围 **2005-02-23 ~ 2026-09-18**。
2026 年逐月均在，37 只 ETF 全覆盖：

| 月份 | 行数 | ETF 数 |
|---|---|---|
| 2026-01 | 740 | 37 |
| 2026-02 | 518 | 37 |
| 2026-03 | 814 | 37 |
| 2026-04 | 777 | 37 |
| 2026-05 | 666 | 37 |
| 2026-06 | 777 | 37 |
| 2026-07 | 851 | 37 |
| 2026-08 | 777 | 37 |
| 2026-09 | 518 | 37 |

（2026-02 与 2026-09 行数偏少是春节假期与月份未走完所致，正常。）

### 修法：默认区间改为「库中最新交易日」，而不是写死

**后端**（`api/src/server/routes/backtest.py`）新增两个辅助函数：

```python
def _latest_data_date() -> str:
    """返回 etf_daily 中最新的交易日。用作回测默认 end_date。"""
    # SELECT max(date) FROM etf_daily, 失败则回落 date.today()

def _resolve_dates(body) -> tuple[str, str]:
    """未提供 (或为空串) 时: start 默认 2020-01-01, end 默认库中最新交易日。"""
    return (body.get('start_date') or '2020-01-01',
            body.get('end_date') or _latest_data_date())
```

三个端点（`/backtest`、`/backtest/compare`、`/backtest/optimize`）原本各自硬编码一份，
**统一改为调用 `_resolve_dates(body)`**。用 `or` 而非 `.get(..., default)` 是为了
同时兜住空串。

**前端**：

- `web/app/types/backtest.ts`：`start_date` / `end_date` 改为**可选**。
- `web/app/pages/strategy.vue`：不再传这两个字段，交由后端解析。

这样**以后新拉的数据会自动纳入回测区间**，不需要再改代码。同时也让 API 调用方
受益（之前不传 end_date 会静默截断到 2025 年底）。

## 用户问「怎么把里面的 ETF 替换为我自选的」——机制与三个坑

### 机制

标的池定义在 `api/src/data/seed/etf_config.py` 的 `ETF_POOL`（dataclass 列表）。
**它只在「拉数据」阶段起作用**，引用点只有三处：

| 文件 | 用途 |
|---|---|
| `data/seed/__init__.py` | 种子流水线（写 etf_info、逐只拉日线/分钟线）|
| `data/enrich.py` | 元数据补全（基金规模/跟踪误差）|
| `server/routes/system.py` | `/system/update` 增量更新 |

界面与 API 读的是**数据库**（PG `etf_info` + DuckDB `etf_daily`），不读池子。
所以「替换池子」= 改列表 + 重建镜像 + **清理旧标的** + 重新拉数。

### 坑 1（最容易被忽略）：旧标的数据不会自动清理

`seed/__init__.py` 是**按 code 删除后再写入**：

```python
ddb.execute('DELETE FROM etf_daily WHERE code = ?', [etf.code])   # 只删本次要写的那只
```

从池子里移除的标的，其 `etf_daily` / `etf_minute` 行、PG `etf_info` 行**全部保留**。
后果：**你以为换掉了池子，实际是叠加** —— 回测照样会交易那些已经删掉的标的。
必须额外手工清理这三处（外加 raw lake 的 `data/raw/etf_daily/<code>/` 目录）。

### 坑 2：个股**可以**放进池子（已实测）

担心点在于取数函数叫 `fund_etf_*`（ETF 专用）。实测结论：**能用**。

`ak.fund_etf_hist_sina` 底层是 Sina 的通用 hisdata 接口（按 sh/sz 代码取数），
个股同样返回：

| 标的 | fund_etf_hist_sina | fund_etf_hist_em(东财) |
|---|---|---|
| 东瑞股份 001201 | 1310 行，最新 2026-09-18 | ConnectionError |
| 贵州茅台 600519 | 6008 行，最新 2026-09-18 | ConnectionError |
| 沪深300ETF 510300 | 3481 行，最新 2026-09-18 | ConnectionError |

（东财在本机环境对**所有**标的都挂，一直走 Sina 降级，故个股不受影响。）

校验器 `_check_ohlc_range()` 只检查 `close > 0` / `high > 0`，**没有价格上限**，
所以茅台这种千元股也能过。（`validator.py` 里也**没有**行数下限检查，
尽管 `etf_config.py` 头部注释声称有「>=252 行」。）

### 坑 3：成功门槛 `MIN_ETF_COUNT = 25` 的计数器是坏的

```python
success_count = _seed_state['success']
if success_count >= MIN_ETF_COUNT:  status = 'ready'
else:                               status = 'error'
```

两个问题：

1. `success` 在**日线循环和分钟线循环各加一次**（第 310、354 行），
   所以实际值 ≈ **2 × 池子大小**，不是池子大小。
2. `run_seed()` 开头只重置 `status`，**从不重置 `success`** —— 跨次累加。

后果：池子小于约 13 只、且是全新环境时，会判 `error`；而
`web/app/middleware/setup.global.ts` 的判断是 `if (data.status !== 'ready') → 跳 /setup`，
**界面会永远跳回初始化页**。反之若之前成功过一次，这个门槛就形同虚设。
替换池子前应先把 `MIN_ETF_COUNT` 调成与池子规模匹配的值（或改为按池子比例计算）。

### 附带发现（小问题，未修）

`/system/status` 的 `etfs_available` 取自内存 `_seed_state['success']`。
api 容器重启后内存清空，走「检查数据库」兜底分支时该字段会变成 `0`（当前实测
`{"status":"ready","etfs_available":0,"etfs_total":37}`）。
不影响中间件（只看 `status === 'ready'`）与回测（直接读 etf_daily），仅显示口径问题。

## ⚠️⚠️ 重大发现：池子价格数据被公司行为污染，回测结果全部不可信

### 现象

用 `tools/qf_scan_price_gaps.py` 扫描 `etf_daily`，以「单日 |涨跌幅| > 11% 不可能是真实行情」
（A 股 ETF 有涨跌停）为判据，**扫出 35 处断层，涉及 18/37 只 ETF**。

其中落在 2025-2026 回测窗口内的：

| 标的 | 日期 | 单日 |
|---|---|---|
| 通信ETF 515880 | 2026-02-03 | **-65.70%** |
| 通信ETF华夏 515050 | 2026-05-13 | **-65.29%** |
| 通信ETF 515880 | 2026-07-06 | -52.06% |
| 芯片ETF 159995 | 2026-07-07 | -50.12% |
| 银行ETF华宝 512800 | 2025-07-07 | -49.69% |

更早的还有 城投债ETF -90%、公司债ETF -90%、医药卫生ETF -74%、
中证500ETF联接 -61%、红利低波 -51%、煤炭ETF -50.3%、酒ETF -48% 等；
以及反向的 公司债ETF +900%、中证500ETF +248%、中证1000ETF +176.9%、
沪深300ETF联接 +159.3%。这些全部是**份额折算/分红**造成的价格断层。

### 已证实污染了回测

取 MA10 在 2020-01-01 ~ 2026-09-18 的回测净值曲线，逐日跌幅排序：

```
2026-02-03   -35.26%   <-- 正是 515880 假断层的日期
2025-09-04    -8.27%
2026-06-26    -6.33%
```

**一个 ETF 组合不可能单日亏 35%。** 即此前报出的所有回测数字
（+5.34% / +58.45% / alpha -18.52% / +33.23% 等）都掺入了这个假暴跌，
**结论不可用**。

### 根因

`clean_etf_data()` 在 `adj_close_ref` 为 None 时直接令 `adj_close = close`，
即**不复权**。而本次 seed 东财源全线 `RemoteDisconnected`/`ConnectionError`、
全部降级走 Sina，Sina 返回的是不复权价，于是 `adj_close` 从未被真正复权过。
这解释了 README「日线尚未启用前复权」的已知限制，但**没人意识到它会让回测出现假暴跌**。

### 现成的前复权源不可用

实测东财 hist 三个变体全部 `ConnectionError`：

```
510300 fund_etf_hist_em(qfq)      : ConnectionError
510300 fund_etf_hist_em(不复权)    : ConnectionError
515880 fund_etf_hist_em(qfq)      : ConnectionError
```

（东财 push2his CDN 屏蔽非浏览器 TLS —— 与代码注释所述一致；
但 `fund_etf_spot_em()`（push2 实时列表）是可用的。）

### 建议修法（待用户确认后实施）

在 `clean_etf_data()` 里增加**断层检测 + 前复权回补**：

1. 在 `close` 上算日收益，检出 `|r| > 21%` 的断层
   （21% 高于任何合法涨跌停，避开创业板/科创板 ETF 真实的 ±20% 涨跌停）
2. 对每个断层日 D：令 `factor = close[D] / close[D-1]`，把 D 之前的全部价格乘以 factor
3. 结果写入 `adj_close`（`close` 保留原始不复权值），供策略使用
4. 重新 seed 以重建 `adj_close`

注意不可用简单的 11% 阈值：创业板ETF、科创50ETF 在 2024-09-30 / 2024-10-08
确有真实的 ±20.00% 涨跌停（20% 限制），误判会破坏真实行情。

### 受影响的候选

新候选 **159507 通信ETF广发** 同样有断层：
2026-06-09 从 3.031 跳到 1.065（**-64.86%**，份额折算）。

## 前端改为经内网穿透地址访问后端（已实施）

用户要求：前端访问后端接口改用 `http://101.42.40.10:10004/`（其 frp 内网穿透地址）。

### 先验证地址指向

```
GET http://101.42.40.10:10004/health               → 200 {"status":"ok"}
GET http://101.42.40.10:10004/api/v1/system/status → 200 (37 只 ETF, 与本地 18000 一致)
GET http://101.42.40.10:10004/docs                 → 200
```
确认就是 quant-fletch 的 FastAPI，即 `101.42.40.10:10004` → 本机 `18000`。

（附带发现：记忆里记的 frp 目录 `C:\Users\Administrator\Desktop\frp` 已不存在，
但隧道本身工作正常。未追查。）

### 关键机制：两个地址都是**构建期**注入的

| 变量 | 作用 | 求值时机 |
|---|---|---|
| `API_BASE_URL` | `nuxt.config.ts` 的 `routeRules` 代理目标（**SSR 侧**请求后端用）| 构建期 |
| `VITE_WS_ORIGIN` | 浏览器侧 WebSocket 直连地址（回测进度推送）| 构建期 (Vite env) |

`nuxt.config.ts` 里已有注释说明：**只在 compose 设 runtime `environment` 无效**，
必须作为 build arg 传进 `nuxt build`。

### 改法

1. `docker/Dockerfile.web`：把写死的 `ENV API_BASE_URL=...` / `ENV VITE_WS_ORIGIN=...`
   改为**带默认值的 `ARG`**，再 `ENV X=$X`，默认值仍为内网直连
   （`http://api:8000` / `ws://localhost:18000`）。
2. `docker/docker-compose.yml` 的 `nuxt.build.args` 传入穿透地址：
   ```yaml
   build:
     args:
       API_BASE_URL: http://101.42.40.10:10004
       VITE_WS_ORIGIN: ws://101.42.40.10:10004
   ```
   （注释里写了改回内网直连的两行。）

### 验证

- 构建产物三处均替换为穿透地址：`public/_nuxt/*.js`、`server/chunks/build/api-*.mjs`、
  `server/chunks/nitro/nitro.mjs`；`localhost:18000` 残留 **0** 处。
- 经 Nitro 代理 `GET localhost:3000/api/v1/system/status` → 200，耗时 **0.057s**。
- 经代理 `POST /api/v1/backtest`（伪造策略名）→ 422 且返回后端结构化错误，
  证明**请求体转发正常**。
- **WebSocket 穿透实测可用**：连 `ws://101.42.40.10:10004/api/v1/backtest/<假id>/ws`
  收到 `{"progress":0.0,"step":"failed","message":"回测运行不存在或已过期"}`。
- 页面 `/`→302（跳 /dashboard）、`/dashboard`、`/strategy` 均 200。

### ⚠️ 代价（已告知用户）

`API_BASE_URL` 指向公网地址后，**SSR 的每次后端请求都要绕一圈公网**
（容器 → 公网 frp → 回本机 API）。实测 57ms 尚可，但
**frp 隧道一旦断开，连本地 localhost:3000 都会 500**。
更稳的做法是 SSR 保持内网 `http://api:8000`、仅把 `VITE_WS_ORIGIN` 设为公网地址
—— 本地与远程都能用且不依赖隧道。

```
match exactly, but along dimension 0, the array at index 0 has size 52
and the array at index 17 has size 0
```

### 根因：空数组混进了 `np.column_stack`

`strategies/multi_factor.py` 的 `_correlation_penalty()`：

```python
if len(adj) < 2:
    ret_series.append(np.array([]))          # ← 空数组照样进列表
    continue
...
min_len = min((len(r) for r in ret_series if len(r) > 0), default=0)   # ← 算最短长度时跳过空数组
ret_matrix = np.column_stack([r[-min_len:] for r in ret_series])       # ← 拼接时却包含空数组
```

两处口径不一致：空数组切 `[-min_len:]` 仍为空 → 拼接尺寸不匹配 → 抛错。

**触发条件**：回测起点早于部分 ETF 的上市日。`get_price_df()` 会从 `start_date`
再前推 365 天缓冲，而池内**共 8 只 ETF 首个交易日晚于 2019-01-01**：

| 代码 | 名称 | 首个交易日 |
|---|---|---|
| 159995.SZ | 芯片ETF | 2020-02-10 |
| 159981.SZ | 能源化工ETF | 2020-01-17 |
| 159980.SZ | 有色金属ETF | 2019-12-24 |
| 515050.SH | 通信ETF华夏 | 2019-10-16 |
| 515880.SH | 通信ETF | 2019-09-06 |
| 512690.SH | 酒ETF | 2019-05-06 |
| 511030.SH | 公司债ETF | 2019-03-22 |
| 512890.SH | 红利低波ETF华泰柏瑞 | 2019-01-18 |

回测从 2020-01-01 起时，最早的调仓日（2020-01-02）上芯片ETF 一行数据都没有 →
必然触发。**这是仓库原有缺陷**，与本次新增的 7 只 ETF 无关（这些标的大多在原始 30 只里）。

### 修法

`multi_factor.py::_correlation_penalty`：先算出有效下标 `valid_idx`，**只对有效序列做
`column_stack`**，再把结果 scatter 回长度 n 的数组（无效标的给中性值 0.3），
保证返回长度与 `codes` 对齐。均值分母改用 `len(valid_idx)-1`，与 corr 维度一致。

`allocation.py::build_cov_from_prices`：**同一处写法有同样的 bug**。
但协方差矩阵的维度必须与 `codes` 一一对应（调用方按下标索引，且后续要
`np.linalg.inv`），所以不能剔除标的凑数 —— 那会得到奇异矩阵、`inv` 抛 LinAlgError。
故改为：只要有标的取不到数据就**返回 `None`**，由调用方回落等权
（`momentum_rotate.py` 与 `trend_ma.py` 都已有 `if cov is not None ... else 等权` 分支）。
该函数仅在 `alloc_method == 'bl'` 时被调用，默认 `'equal'` 不触发，属潜在 bug。

## 修复 3：引擎层「目标组合」模式（用户选定方案 1）

解决了「5 个内置策略只买不卖」的结构性问题。

### 设计：策略声明仓位语义，引擎负责核对

在 `StrategyMeta` 新增字段 `position_mode`（默认 `'incremental'`）：

- `'incremental'`（默认）—— `allocate()` 发的是**增量指令**（买哪些/卖哪些），
  引擎不动它没提到的持仓。适合自管买卖的策略（MA10）。
- `'target'` —— `allocate()` 发的是**当期目标组合**（buy 权重之和 ≈ 1），
  引擎在调仓日自动卖出目标之外的持仓。适合轮动类策略。

**为什么必须显式声明而不能一刀切**：`MA10 趋势跟踪` 的设计是「只对新标的发 buy、
跌破均线才发 sell」，属增量语义。若引擎无条件卖出"不在买入列表里"的持仓，
会把它的存量仓位全清掉、直接搞坏。默认值取 `incremental` 保证零破坏。

### 引擎改动（`backtest/self_loop.py`）

新增 `_reconcile_target_portfolio(signals, portfolio)`，在 `risk_overlay` 之后、
`generate_signals` 之前调用（仅当 `position_mode == 'target'`）：

1. 持有 且 不在目标内 → **卖出**（整仓清出）
2. 持有 且 在目标内 → 转为 `hold`，**不再买入**
   —— 因为引擎的买入按 `total_equity × 权重` 算目标成本而非增量，
   对已持有标的再发 buy 会在原仓位上再加一遍、导致超配
3. 未持有 且 在目标内 → 保留原 buy，由引擎分配卖出释放的现金

卖出列表**显式排序**（引擎逐笔累加现金对顺序敏感，顺序不定会导致不可复现）。

### 顺带修 `generate_signals` 的持仓计数

原实现 `[s for s in signals if s.action != 'hold']` 会把 **sell 也算作持仓**，
加了自动卖出后数字明显偏大。改为 `buy + hold` 计数。

### 声明为 target 的 5 个策略

`双均线动量轮动`、`行业轮动`、`趋势+均线择时`、`多因子综合打分`、`波动率加权风险平价`。
