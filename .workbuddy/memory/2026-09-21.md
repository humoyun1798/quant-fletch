**没有任何一个策略在多数窗口跑赢基准。** 这与之前"换个区间结论就反转"的观察一致 ——
说明此前看到的收益主要来自**特定行情的 beta**，不是稳定的 alpha。

### 它们共同的"性格"：低 beta、防守型

| 年份 | 2022 | 2023 | 2024 | 2025 | 2026 |
|---|---|---|---|---|---|
| 基准 510300 | -21.7% | **-10.4%** | **+18.4%** | +21.5% | **-1.0%** |

### 期间踩的坑

1. **报告写到容器内 `/tmp` 会丢** —— 容器 `--rm` 退出后文件没了。
   改为挂载宿主机目录 + 同时打印到 stdout 兜底。

## 用户报障：「数据初始化失败」（实为误报，数据完好）

### 真相

**数据一行没丢**，是**前端连不上后端**，被中间件跳到了 `/setup` 页，
用户看到"数据初始化"页就以为初始化失败。

| 检查项 | 结果 |
|---|---|
| `etf_daily` | 76,391 行 / 34 只 / 最新 2026-09-18 ✓ |
| `sector_daily` | 82,728 行 ✓ |
| `etf_sector_map` | 15 行 ✓ |
| `/system/status` | `status=ready, etfs_available=34` ✓ |
| `101.42.40.10:10004/health` | **HTTP 000（内网穿透断了）** |
| `localhost:18000/health` | 200 ✓ |

**证据链**：经前端 Nitro 代理访问 `localhost:3000/api/v1/system/status` → **502**
（代理目标是穿透地址）；构建产物里写死的就是 `http://101.42.40.10:10004`。

**正是先前把 `API_BASE_URL` 指向公网时警告过的代价**：
`setup.global.ts` 中间件在 fetch 失败时 `navigateTo('/setup')`，
于是隧道一断 → 界面显示初始化页 → 用户去点"初始化"按钮 →
**那个按钮走同一条断掉的链路、同样失败（502）** → 显示"初始化失败"。

### 修复（两处）

1. **`docker/docker-compose.yml`**：`nuxt.build.args` 改回
   `API_BASE_URL: http://api:8000`（内网直连）+ `VITE_WS_ORIGIN: ws://localhost:18000`。
   **SSR 侧必须走内网** —— 它是服务端请求，绕公网没有任何好处，只会引入隧道依赖。
   注释里写清了「要不要走公网、什么场景下才改」。
2. **`web/app/middleware/setup.global.ts`**：区分「API 不可达」与「数据未初始化」。
   原实现两者都跳 `/setup`，会**误导用户去点初始化**（且必然失败、还可能白跑一次
   全量重拉）。改为 fetch 失败时放行，由页面自身呈现取不到数据的状态。

### 验证

- 产物：`http://api:8000` ✓，穿透地址残留 **0** 处
- 经代理 `GET /api/v1/system/status` → **200**
- `/dashboard` **302 → 200** ✓、`/strategy` 200、`/setup` 200
- WS 地址 `ws://localhost:18000`；经代理取 `/api/v1/etfs` → 34 只

### 附带：Docker 恢复

用户已重启 Docker Desktop，`docker ps` 恢复正常，三个容器 healthy。

### 教训

**SSR 侧的后端地址绝不要指向公网穿透地址。** 服务端请求走内网即可，
只有浏览器侧直连的 WebSocket 才需要考虑公网。
把公网地址用在 SSR 上，会把"隧道可用性"变成整个界面的单点故障。

## 用户需求：为 7 个策略找最优参数并设为默认

### ⚠️⚠️ 过程中发现的严重缺陷：「行业轮动」结果不可复现（已修）

同一组参数 `{lookback:60, top_n:3, sector_weight:1.0}` 连续跑：
**+169.31% / +150.74% / +117.19%**（三个不同净值指纹）。
另外两次扫描同一组参数给出 **+133.5%** 与 **+94.7%** —— 最大差 **52 个百分点**。

**根因**：`sector_weight=1.0` 时同一行业下所有 ETF 得分**完全相同**（都取行业动量），
并列极多；而 `allocate()` 里 `sorted(scores.items(), key=lambda x: x[1], reverse=True)`
是**稳定排序** —— 只按 value 排序时，并列名次由 dict 的**插入顺序**决定。
插入顺序又来自两个不保证稳定的地方：

1. `SELECT ... FROM sector_daily WHERE date <= ?` **没写 ORDER BY**（DuckDB 不保证扫描顺序）
2. polars `group_by()` **不保证输出行顺序**（这是本仓库已记录过的坑）

**修法（sector_rotate.py 四处）**：
1. sector_daily 查询加 `ORDER BY industry_code, date`
2. `sector_mom` 聚合后加 `.sort('industry_code')`
3. `for etf_code in sorted(universe)`（scores 插入顺序确定）
4. `allocate()` 的排序键改为 `lambda x: (-x[1], x[0])` —— **以 code 作次级键打破并列**

**验证**：修复后同参数连跑 3 次，收益与指纹**完全一致**（`eddc629a9526`）。
默认参数仍为 +25.53%、指纹 `01d4232e81fc`（与修复前一致 → 修复未改变正常行为，
只是让它可复现）。

**教训**：**任何依赖排序的选股逻辑，都必须给并列排名一个确定的次级键。**
只要分数可能并列（等权、同行业、同分档），插入顺序就会决定选中谁。

其它 6 个策略经两次独立扫描，同参数结果**逐一对上**，未发现同类问题。

### 最终结论与已设默认参数

判定「最优」不只看收益，还要看**最优点是不是平台**：邻近参数突然变差 = 撞运气。
以下 4 个策略的改动**同时满足**「收益大幅提升」+「邻域平稳或规律系统性」+「结果可复现」：

| 策略 | 改动 | 依据 | 可信度 |
|---|---|---|---|
| MA10 趋势跟踪 | `max_deviation` 0.015 → **0.01** | 0.8%/1.0%/1.2% → 112%/101%/100%（夏普 0.60/0.54/0.50）；1.5% 仅 53.5%、2% 降到 29.5% | **高**（平台）|
| 行业轮动 | `top_n` 5 → **3**、`sector_weight` 0.7 → **1.0** | sw=1.0 在 lookback×top_n 全 **6/6** 组合下都优于 0.5；top_n=3 在 3 个 lookback 下 **3/3** 优于 5 | **高**（系统性）|
| 趋势+均线择时 | `top_n` 5 → **3**、`ma_period` 200 → **60** | ma 40/60/80 → 34.4%/42.1%/44.8%（平稳递增）；原 200 只有 7.9% | 中高 |
| 多因子综合打分 | `lookback` 60 → **20**、`top_n` 5 → **8** | lb 15/20/25 → 27.2%/64.7%/52.7% | 中（局部高点）|

**不动默认值的 3 个策略（最优点是尖峰 = 过拟合，拒绝改）**：

| 策略 | 现象 |
|---|---|
| 双均线动量轮动 | top_n=3 时 lookback 50/60/70/80 → 41.3%/**58.5%**/22.7%/27.1%；且 top_n 无一致偏好（lb=60 时 n3 好、lb=20/40/120 时 n8 好）|
| 波动率加权风险平价 | lookback 100/**120**/140 → 30.9%/**62.4%**/20.0%，典型尖峰 |
| 带止损动量增强 | lookback 100/**120**/140 → 33.1%/**47.8%**/**-2.5%**，尖峰；且**原默认就是最稳的**（6/7 年正收益、回撤最佳 -21.0%）|
